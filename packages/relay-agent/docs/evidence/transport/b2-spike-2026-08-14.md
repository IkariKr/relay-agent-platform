## 3. 为什么 spike 现在不能执行

1. **付费红线**：B2 最小 spike 需要真实调用第三方 provider（DeepSeek 计费）。roadmap §10 红线："paid smoke、写 worker、敏感数据外发必须显式授权"。本记录日期未获用户对该 spike 的显式授权，因此不得执行。
2. **宿主能力未知**：A2 evidence 显示 spawn/isolation/callback/plaintext 全部为 unknown，属于"需活宿主"行为。在没有能力证据前运行 spike，违反"行为证据优先"原则。
3. **pack 注册格式未验证**：`[agents]` 段缺失，B1 只做了 pack-owned 文件暂存；config.toml 的 role 注册语法需先由配置解析验证，否则 spike 无法以正确形态创建 child。

结论：即使获得授权并设置凭据，0.142.5 的 agent 注册格式未验证 + 无 spawn 开关，**完整 native-child identity 的 B2 spike 在本版本大概率无法完成**；可做的只是"custom provider 的 plaintext marker 经 `codex exec` 到达模型 + 回调"的部分证据（仍属 B4 前的不充分证据）。

## 4. 决策（roadmap §8.2 退路分支）

- **B2 延期**（defer）：不在本环境未授权状态下执行付费 spike。
- **B3 不进入**：没有证据证明"native spawn/lifecycle 可用、仅 task delivery 被阻断"，不满足进入 Hook spike 的前置条件。
- **B4 延期**：paid smoke 属显式授权操作，未授权前不执行；README 不宣称 DeepSeek 为 supported native child（claim gate 保持）。
- **不伪造 native**：不用 CLI/SDK/MCP/第二 Codex 冒充 native child（roadmap §1 条件 5、§8.2 第 4 条）。
- 当前交付状态 = **A0-A2 + B1 完整**；external-cli 路线继续可用；Worker Runtime Registry、capability probe、DeepSeek pack、dispatch（Phase C）均可独立演进。

## 5. 重开条件

当以下条件**全部**满足时，用新 evidence 重开 B2/B3，无需推翻 Worker Registry：

1. 用户显式授权付费 spike（同意 DeepSeek 计费）；
2. `DEEPSEEK_API_KEY` 已设置且经 `Test-WorkerSecretPreflight` 存在性验证（值不打印）；
3. provider 命名对齐：pack 假设 provider id `deepseek` + `env_key=DEEPSEEK_API_KEY`，当前配置为 `custom`——用户需将 provider 配置改为 `deepseek`（或 pack 提供别名映射）；
4. Codex 版本具备已验证的 `[agents]` 注册格式与 native-child 行为（参考基线：0.146.0 + Hook，且需重新探测上游缺陷状态）；升级后重新运行 capability probe 生成新 host evidence；
5. 重新生成 capability evidence 并据此执行 B2 → B3（仅当 evidence 指示）→ B4。

之后按 roadmap Phase B2 → B3（仅当 evidence 指示）→ B4 顺序推进。
